# Production Deployment Checklist

Use this checklist when deploying Smart Presentations to a real environment.
Each item is tied to the current codebase state as of the latest cleanup.

## Pre-Deployment Verification

### Code & Configuration
- [ ] `pnpm run doctor` reports no problems (it checks `.env`, `node_modules`, the Node version and the pinned pnpm version; it prints variable **names** only, never values)
- [ ] `pnpm type` passes cleanly
- [ ] `pnpm lint` passes cleanly
- [ ] `pnpm test:unit` passes cleanly
- [ ] `pnpm build` succeeds in a memory-sufficient environment (>=4GB RAM)
- [ ] Node.js 22 is used everywhere (`node:22-alpine` in `Dockerfile`, `node-version: "22"` in CI, `NODE_VERSION = "22"` in `netlify.toml`); Next.js 16 requires Node >= 20.9
- [ ] pnpm 10.34.6 is used via Corepack (pinned by the `packageManager` field in `package.json`)
- [ ] No references to `NextAuth`, `next-auth`, `@prisma/client`, `SupabaseAuthProvider`, or `supabase-provider` remain in `src/`
- [ ] `.env.example` matches the required production variables

> Note on `pnpm doctor`: pnpm ≥10 ships its own `doctor` command for diagnosing the
> *pnpm installation*, and built-in commands win over `package.json` scripts. Use
> `pnpm run doctor` (or `pnpm preflight`, an alias with no name collision) to run
> this repo's environment check.

### Required Environment Variables

`src/env.js` is the schema; `.env.example` is the annotated template. Only these
three are declared without `.optional()`, so `pnpm build` and `pnpm dev` fail
immediately while any of them is unset:

- [ ] `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` — Clerk Dashboard → API Keys → Publishable key
- [ ] `CLERK_SECRET_KEY` — Clerk Dashboard → API Keys → Secret key
- [ ] `DATABASE_URL` — Supabase Dashboard → Project Settings → Database → Connection string (see the Supabase-only requirement below)

Optional in the schema (`.optional()` or defaulted — an unset value never blocks
start-up, it only disables the feature named in `.env.example`):

- [ ] `CLERK_WEBHOOK_SECRET` — **not configured today**, see "Required secrets not yet configured"
- [ ] `OPENAI_API_KEY` — **not configured today**, see "Required secrets not yet configured"
- [ ] `UPLOADTHING_TOKEN` — **not configured today**, see "Required secrets not yet configured"
- [ ] `NEXT_PUBLIC_SUPABASE_URL`
- [ ] `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- [ ] `SUPABASE_SERVICE_ROLE_KEY` (needed for server-side admin writes that bypass anon RLS)
- [ ] `API_KEY_ENCRYPTION_MASTER_KEY` — 32 bytes, generate with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`. Required for storing per-user OpenAI keys server-side; rotating it makes already-stored keys undecryptable, so treat the value as permanent
- [ ] `TOGETHER_AI_API_KEY`, `PINECONE_API_KEY`, `TAVILY_API_KEY`
- [ ] `UNSPLASH_ACCESS_KEY`, `PIXABAY_API_KEY`, `GIPHY_API_KEY`, `PEXELS_API_KEY`
- [ ] `GOOGLE_CUSTOM_SEARCH_API_KEY` + `SEARCH_ENGINE_CX`
- [ ] `NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_DSN`
- [ ] `NODE_ENV` (`development` | `test` | `production`, defaults to `development`)

Never set `SKIP_ENV_VALIDATION` in production. It is read directly by
`src/env.js` (it is not part of the schema) and setting it to `true`/`1` disables
every check, which is exactly how a missing Clerk key or `DATABASE_URL` reaches
runtime as an opaque failure instead of an up-front error.

### Required Secrets Not Yet Configured

Three variables are unset in every environment today. All three are optional in
`src/env.js`, so nothing fails at build time — the breakage appears only when the
feature is used, which is why it has gone unnoticed.

| Variable | What it is | Where to get it | What breaks without it |
|---|---|---|---|
| `OPENAI_API_KEY` | Server-side OpenAI key, used whenever a request does not carry its own `apiKey` | https://platform.openai.com/api-keys | Every AI generation endpoint returns **400**: outline generation, slide generation, image generation, and the presentation agent reports "No OpenAI API key is configured". The app generates nothing unless each user first adds their own key under `/settings`. |
| `UPLOADTHING_TOKEN` | Server-side UploadThing API token | https://app.uploadthing.com → API Keys | Browser uploads to `/api/uploadthing` fail signature verification. The server-side `utapi.uploadFiles()` paths used by the image routes keep working. |
| `CLERK_WEBHOOK_SECRET` | Svix signing secret for `/api/webhooks/clerk` | Clerk Dashboard → Webhooks → Add Endpoint (procedure below) | `POST /api/webhooks/clerk` returns **500**, so Clerk users are never synced into the Supabase `public.users` table. |

#### `CLERK_WEBHOOK_SECRET` — exact procedure

This secret cannot be fetched from an API. It is generated by the Clerk Dashboard
as a by-product of creating a webhook endpoint, and it is shown **once**:

1. Deploy the app so that `<origin>/api/webhooks/clerk` is publicly reachable
   (Clerk cannot deliver to `localhost`).
2. Clerk Dashboard → **Webhooks** → **Add Endpoint**.
3. Endpoint URL: `https://<your-origin>/api/webhooks/clerk`.
4. Subscribe to `user.created`, `user.updated` and `user.deleted`.
5. Copy the **Signing Secret** (`whsec_...`) shown for the new endpoint.
6. Store it as `CLERK_WEBHOOK_SECRET` and restart the app. The route reads the
   variable at module load, so a redeploy is required.
7. If the value is lost, delete the endpoint and create a new one — it cannot be
   revealed again.
8. Verify with `WEBHOOK_SECRET=<whsec_...> node scripts/test-webhook.mjs`; an
   unsigned or mis-signed delivery must return 400.

### `DATABASE_URL` Must Point at Supabase

`supabase/migrations/*.sql` are Supabase migrations and depend on Supabase
internals that a vanilla `postgres` image does not have:

- `002_users_and_trigger.sql` — `public.users.id references auth.users(id)` plus a trigger on `auth.users`
- `007_rls_policies.sql` — 35 RLS policies that call `auth.uid()`
- `009_seed_anonymous_user.sql` / `010_cleanup_anonymous_users.sql` — read and delete from `auth.users`
- `011_user_asset_storage.sql` — `storage.buckets`, `storage.objects`, `storage.foldername()`

`scripts/db-push.mjs` applies files in numeric order with no Supabase detection, so
pointing `DATABASE_URL` at a local Postgres container aborts at migration 002 and
every later migration silently never runs. `docker-compose.yml` therefore ships no
local Postgres container and requires `DATABASE_URL` to be the real project:

- Supabase Dashboard → Project Settings → Database → Connection string, session mode
  (`postgresql://postgres.<project-ref>:<password>@db.<project-ref>.supabase.co:5432/postgres`)
- or the Session-mode pooler host `aws-0-<region>.pooler.supabase.com`

Migrations are then applied either with the Supabase CLI
(`supabase link --project-ref <ref> && supabase db push`) or with `pnpm db:push`
against the Supabase connection string.

### Supabase Configuration

- [ ] Supabase project is created and active
- [ ] `NEXT_PUBLIC_SUPABASE_URL` matches project URL
- [ ] `NEXT_PUBLIC_SUPABASE_ANON_KEY` is set
- [ ] `SUPABASE_SERVICE_ROLE_KEY` is set (for server-side admin access)
- [ ] `DATABASE_URL` points at the Supabase project host (see "`DATABASE_URL` must point at Supabase" above), not a local Postgres container
- [ ] Connection pooling is configured for production (Session-mode pooler, `aws-0-<region>.pooler.supabase.com`)
- [ ] Database migrations are applied: `pnpm db:push` (or `supabase db push`)
- [ ] RLS policies are active (see `supabase/migrations/007_rls_policies.sql`)
- [ ] Anonymous user row exists in `public.users` with `role = 'USER'` and `has_access = false`

- [ ] `NEXT_PUBLIC_SENTRY_DSN` is set

## Post-Deployment Verification

### Health & Auth
- [ ] `GET /api/health` returns `{"status":"healthy","database":"connected"}`
- [ ] `GET /` loads without errors
- [ ] `GET /presentation` redirects to `/auth/signin` when not authenticated
- [ ] Sign-in flow works end-to-end
- [ ] After sign-in, user is redirected to `/presentation`
- [ ] Sign-out flow works

### Core Features
- [ ] Can create a new presentation
- [ ] Can generate an AI outline
- [ ] Can generate full presentation from outline
- [ ] Can edit slides in the Plate.js editor
- [ ] Can export to PPTX
- [ ] Can export to PDF
- [ ] Image generation works (requires `OPENAI_API_KEY`, or a user-supplied key in `/settings`)
- [ ] Theme selection and customization works
- [ ] Clerk user rows appear in Supabase `public.users` after a sign-up (requires `CLERK_WEBHOOK_SECRET` and the webhook endpoint)

### API & Security
- [ ] Rate limiting is active (test with rapid requests to `/api/health`)
- [ ] CSRF protection is active (test POST to `/api/ai/copilot` without origin header)
- [ ] Security headers are present:
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
  - `X-XSS-Protection: 1; mode=block`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
  - `Strict-Transport-Security` in production
- [ ] Clerk webhook endpoint returns 400 for invalid signatures (test with `svix` CLI or curl)

### CI/CD
- [ ] GitHub Actions workflow is triggered on PR
- [ ] Type-check job passes
- [ ] Lint job passes
- [ ] Unit tests job passes
- [ ] Build job passes
- [ ] Deploy job runs on merge to `main` (if configured)

## Rollback Plan

If deployment fails:

1. **Vercel**: Rollback to previous deployment from Vercel dashboard
2. **Netlify**: Rollback to previous deploy from Netlify dashboard
3. **Docker**: redeploy previous image tag
4. **Database**: `pnpm db:push` is idempotent; re-run if migrations failed mid-apply

## Known Limitations

- Full `pnpm build` requires >=4GB RAM; CI runners should specify `NODE_OPTIONS="--max-old-space-size=4096"`. This is already set in `netlify.toml`, the CI `build` / `bundle-analysis` / `deploy` jobs, and the `Dockerfile` builder stage — keep it set if you add another build environment.
- Anonymous users can read public content but cannot create/edit presentations unless signed in
- `users.role` and `users.has_access` columns are deprecated; authz now uses Clerk `publicMetadata`
- PPTX/PDF export requires all slides to be visible in the DOM at export time
- E2E pins a single port: `playwright.config.ts` reads `PORT` (default `3000`) and passes it to `pnpm dev --port`, so `next dev` can no longer drift to `3001`. `tests/global-setup.ts` still hardcodes `http://localhost:3000`, so running E2E on a non-default port also requires updating that file.
- `.env` and `node_modules/` are git-ignored, so a worktree reset deletes both and the next `pnpm build` fails with a raw t3-env error. Run `pnpm run doctor` after any reset; it names the missing variables and where to get each one.
